# 每日基础技术总结 · 2026-08-21 · Node.js 事件驱动与非阻塞 I/O

## 📚 今日主题

> **Node.js 事件驱动与非阻塞 I/O**（后端基础（Node.js / Java / Python））

### 1. 核心概念速览
Node.js 的事件驱动与非阻塞 I/O 是构建在其运行时底层的并发模型。事件驱动指的是程序流程由事件（I/O 完成、定时器到点、信号触发）而非顺序调用驱动；非阻塞 I/O 指调用异步 I/O API 时立即返回，不等待内核完成操作，而是由 libuv 在后台监听文件描述符或通过线程池模拟异步，待操作完成后向事件循环注册事件，再由主线程执行回调。它解决的是传统阻塞式 I/O 下线程被 I/O 等待占用、导致高并发场景下资源浪费的问题，用单线程 + 事件循环的协作式调度取代多线程阻塞调度，从而在维持高吞吐的同时降低线程切换与内存开销。在体系上，这是 Node.js 与浏览器共享 JavaScript 事件循环模型的后端延伸，也是所有异步 API、Promise、async/await 的底层地基。专业工程师必须理解其机制，否则无法正确预估异步顺序、排查死锁/内存泄漏、设计高并发服务，也无法区分 CPU 密集与 I/O 密集场景下的不同优化策略。

### 2. 底层原理剖析
底层机制由 libuv 实现。核心是事件循环（event loop），其运行模型为：主线程顺序执行 JavaScript 代码，遇到异步 I/O 调用时，将请求封装成任务提交给底层。对于网络 I/O，通过 epoll/kqueue 注册文件描述符，内核就绪后通知 libuv；对于文件 I/O，libuv 使用线程池（默认大小 4）模拟异步。任务完成后，libuv 将回调放入对应阶段的事件队列。事件循环在每次迭代中按固定顺序轮询各阶段：timers（执行到期的 setTimeout/setInterval 回调）、pending callbacks（处理上一轮残留的错误回调）、idle/prepare（内部使用）、poll（获取新 I/O 事件并执行 I/O 回调，若无其他待办则阻塞等待）、check（执行 setImmediate）、close callbacks（处理关闭事件）。每个阶段之间会执行微任务队列（process.nextTick 优先于 Promise）。非阻塞的本质是：发起 I/O 后主线程不等待，事件循环只有在 poll 阶段才会阻塞等待 I/O 事件，但若存在更高优先级任务（如 setImmediate 或到期定时器），阻塞会被打断。对比前端已有概念：浏览器的事件循环是宿主（浏览器）提供的异步机制，核心是宏任务/微任务队列，没有 poll 阶段（渲染步骤独立）；Node 的事件循环由 libuv 实现，有明确的阶段划分，且 I/O 事件直接驱动循环推进。正如 TS 接口与 Java 接口虽然在语法上相似，但一个是编译期结构约束，一个是运行期多态契约；浏览器和 Node 的异步模型虽然都基于 JS 的单线程回调，但底层调度逻辑和资源模型不同，不能直接套用。Node 的微任务行为在 Node 11 后与浏览器趋同，但 process.nextTick 仍是 Node 独有的高优先级队列，这是设计上为了允许在事件循环阶段切换前执行紧急清理或重试。理解这个差异，才能解释为什么某些异步顺序在浏览器和 Node 中表现不同。

### 3. 基础代码与实战验证
```text
const fs = require('fs');

// 异步读取文件：发起请求后立即返回，底层 libuv 将任务交给线程池/内核
fs.readFile(__filename, 'utf8', (err, data) => {
  // 这个回调不会立即执行，而是由事件循环在 poll 阶段取出执行
  console.log('I/O 回调执行');
});

// 同步代码继续执行，不会被上面异步调用阻塞
console.log('同步代码执行');

// 模拟一个耗时 100ms 的 CPU 密集型同步任务
// 此时主线程被占住，事件循环无法运行，所以 I/O 回调不会执行
const start = Date.now();
while (Date.now() - start < 100) {}
console.log('同步耗时任务结束');

// 主线程调用栈清空后，事件循环才能从 poll 队列取出 I/O 回调执行
// 因此输出顺序为：
// 同步代码执行
// 同步耗时任务结束
// I/O 回调执行
```

### 4. 常见误区与进阶思考
误区 1：认为 Node.js 是单线程的。实际上单线程指的是 JavaScript 执行线程，而 libuv 内部维护了一个线程池用于文件 I/O、DNS 查询等操作，操作系统内核也参与异步网络 I/O。因此 Node.js 的整体运行是多线程协作的，只是这些线程不执行 JS 代码。误区 2：将非阻塞 I/O 等同于并发执行代码。非阻塞 I/O 只保证发起 I/O 时不阻塞主线程，但回调本身仍同步占用主线程；如果回调中有耗时 CPU 操作，会阻塞后续所有事件，导致事件循环延迟。CPU 密集任务应该使用 worker_threads 或子进程。思考题：为什么 process.nextTick 的回调会先于 Promise 的 then 回调执行？请结合事件循环的队列设计说明其意图，并指出这种设计在何种场景下可能导致“饥饿”。
