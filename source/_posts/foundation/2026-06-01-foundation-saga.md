# 每日基础技术总结 · 2026-06-01 · Saga 分布式事务的补偿机制

## 📚 今日主题

> **Saga 分布式事务的补偿机制**（后端基础）

### 1. 核心概念速览
Saga 是分布式事务领域的一种一致性模式，属于分布式系统理论中事务协议族（2PC、TCC、Saga、本地消息表/Outbox）之一，解决的是跨服务、跨数据库的多个本地事务如何收敛为『要么全部生效、要么全部被抵消』的问题。其本质定义是：将一个全局业务事务分解为有序的本地事务序列 T1, T2, ..., Tn，每个 Ti 在自己的数据库内以 ACID 语义独立提交；同时为每个 Ti 预先定义补偿事务 Ci，Ci 的职责是在业务语义层面撤销 Ti 已对外产生的副作用。执行规则只有两条：正向顺序执行 Ti，全部提交即全局成功；若 Tk 失败，则逆序执行 C(k-1), ..., C1，使系统收敛到等价于全局未执行的状态。

Saga 解决的问题是 2PC 在分布式环境下的可用性缺陷：2PC 通过准备阶段加锁、提交阶段协调来保证强原子性，但任一参与者不可用会导致全局阻塞；Saga 放弃全局锁与强隔离，换取高可用与最终一致性，属于 BASE 模型的具体实现。其机制的核心区分是『补偿』而非『回滚』：回滚是存储引擎基于 undo 日志在物理层执行的逆操作，发生在事务提交前，且不可能失败；补偿是应用层执行的语义逆操作，发生在事务提交后，可能失败、必须重试、必须幂等。因此 Saga 提供的原子性是『假设补偿最终必然成功』的收敛性保证，而非数据库式的确定性保证。

在计算机体系中的位置：位于分布式系统理论、CAP/BASE、事件驱动架构的交汇处，是微服务架构中订单、支付、库存等跨服务写路径的必备基础设施能力。专业工程师必须掌握它，因为跨服务写入在现代系统中无法回避；只有理解补偿与回滚的本质差异、隔离性缺失的后果、幂等与持久化的必要性，才能正确设计故障恢复路径，并判断何时选用 Saga、何时选用 2PC 或本地消息表。

### 2. 底层原理剖析
一、形式化模型
Saga 是二元组序列 S = {(T1,C1), (T2,C2), ..., (Tn,Cn)}。Ti 是第 i 个本地事务，在参与者各自的数据库内以 ACID 语义独立提交；Ci 是 Ti 的补偿事务，只在 Ti 提交后才可能被调用。补偿的对象是『已提交的副作用』，而非『未提交的数据』——这是与数据库回滚的根本分界：回滚发生在提交前、由 undo 日志驱动、不执行业务逻辑；补偿发生在提交后、由业务代码驱动、会创建新的数据状态。

二、执行与收敛规则
正向路径：T1 → T2 → ... → Tn 顺序执行，全部成功即全局完成，无全局提交动作。反向路径：若 Tk 抛错，则执行 C(k-1) → ... → C1，完成后 Saga 终止。执行顺序必须严格逆序，因为 Ci 只保证撤销 Ti 的副作用，乱序执行会破坏前置补偿的语义前提。若 Ci 自身失败，必须持久化失败标记并重试（指数退避）直至成功；重试要求 Ci 幂等。另需注意：并非所有失败都必须补偿，对瞬时故障（如网络超时），正向重试 Tk 往往优于逆序补偿，因为补偿本身也有成本与二次失败风险；选择正向恢复还是反向补偿，取决于失败类型与业务约束。

三、协调模型
编排模式（Orchestration）：中央协调器维护 Saga 状态机，显式向各参与者下发 execute/compensate 指令。状态机最小集合为 INIT、EXECUTING(Ti)、SUCCEEDED、FAILED、COMPENSATING(Ci)、COMPENSATED；每次状态迁移必须先持久化再执行动作，否则进程崩溃后无法恢复执行点。协同模式（Choreography）：无中央协调器，参与者完成 Ti 后发布领域事件，后续参与者订阅并执行 T(i+1)；某步失败则发布失败事件，前序参与者订阅后执行补偿。协同模式耦合度更低，但全局执行序列隐式分布在事件拓扑中，难以观测与治理，且事件乱序可能导致补偿错乱。

四、持久化根基
执行 Tk 之前，协调器必须将『Saga 进入 Tk』的日志记录与 Tk 的本地业务写入放在同一个本地数据库事务中（事务性发件箱模式）。补偿同理：执行 Ck 前持久化『Ck 开始』，完成后持久化『Ck 完成』。没有持久化的执行栈，进程一旦崩溃就丢失补偿依据，系统永久停留在中间态。这是 Saga 工程实现与理论模型的临界点。

五、隔离性缺失与对策
Saga 明确放弃隔离性（I）：T1..Tn 执行期间，中间状态对外可见，并发读会观察到不一致视图。对策包括：语义锁（状态字段预留，如订单置为 PENDING，拒绝冲突操作）、可交换操作（操作结果与顺序无关，天然免疫中间态）、重读校验（执行前重新读取并验证前置条件）、枢轴事务（最后改变业务状态、之后不再需要补偿的步骤）。

六、与前端已有概念的本质对照
1) Saga 补偿对应前端命令模式/Redux 中的 undo：撤销一个 action 不是改写历史记录（物理回滚），而是派发一个语义相反的 action 去抵消其副作用；区别在于前端 undo 在同一内存作用域内同步完成，Saga 补偿跨进程、跨网络，因此必须显式声明、幂等、可重试。
2) 2PC 与 Saga 的契约强度差异，等价于 Java 接口与 TS 接口的差异：Java 接口是名义型契约，类型绑定到显式声明的名字，编译期强制、运行期由具体类实现兜底，类似 2PC 用全局锁与准备阶段在物理层强制各参与方『同生共死』；TS 接口是结构型契约，编译期按形状校验、运行期完全擦除，类似 Saga 不在物理层加锁，而是约定『只要 Ci 在业务语义上抵消 Ti，整个序列就等价于原子』。前者靠机制强制，后者靠语义约定收敛——这正是 Saga 的 Ci 设计必须与业务规则深度绑定、而非简单做数据逆操作的原因。

### 3. 基础代码与实战验证
```text
// ============ 极简 Saga 编排器（编排模式，内存版） ============
// 核心抽象：一个 Saga 步骤 = 一个本地事务 execute + 一个语义补偿 compensate
interface SagaStep {
  name: string;
  execute: () => Promise<void>;    // 本地 ACID 事务，独立提交，提交后副作用对外可见
  compensate: () => Promise<void>; // 语义补偿：在业务层面抵消 execute 已产生的副作用
}

async function runSaga(steps: SagaStep[]): Promise<void> {
  const executed: SagaStep[] = []; // 已成功提交的步骤栈 —— 只有栈内步骤需要补偿

  for (const step of steps) {
    await step.execute();          // 正向路径：提交第 i 个本地事务
    executed.push(step);           // 仅提交成功才入栈；若抛错则不入栈，因为它从未生效
  }
  // 走到此处表示全部成功：各本地事务已各自提交，Saga 全局成功，无显式提交动作

  // 若某步抛错，进入补偿路径：从栈顶逆序执行补偿，LIFO 与依赖顺序严格一致
  for (let i = executed.length - 1; i >= 0; i--) {
    try {
      await executed[i].compensate();
    } catch (e) {
      // 补偿失败不能吞掉：上层必须持久化失败状态并重试（依赖幂等）直至成功，
      // 否则系统停留在中间态 —— 这就是 Saga 原子性只是『最终收敛』而非『物理保证』的原因
      throw new Error('Saga compensation failed at step: ' + executed[i].name, e as Error);
    }
  }
  throw new Error('Saga failed, all executed steps compensated');
}

// ============ 验证：下单三步骤 ============
await runSaga([
  {
    name: 'createOrder',
    // 生产实现中，此处与『写入 Saga 日志』必须在同一个本地事务内完成（事务性发件箱）
    execute: async () => { await db.insert('orders', { id: 'o1', status: 'CREATED' }); },
    // 补偿不是物理删除，而是状态迁移到 CANCELLED —— 保留审计痕迹，且可安全重试
    compensate: async () => { await db.update('orders', { id: 'o1', status: 'CANCELLED' }); },
  },
  {
    name: 'deductStock',
    execute: async () => { await db.decrement('inventory', { sku: 'A', qty: 1 }); },
    compensate: async () => { await db.increment('inventory', { sku: 'A', qty: 1 }); }, // 语义逆操作
  },
  {
    name: 'chargePayment',
    execute: async () => { await paymentApi.charge('o1', 100); },
    compensate: async () => { await paymentApi.refund('o1', 100); }, // 退款 ≠ 删除支付记录
  },
]);
// 若 chargePayment 失败，逆序执行：refund（若已扣款）→ increment 库存 → 订单置为 CANCELLED
```

### 4. 常见误区与进阶思考
误区一：『补偿就是回滚』
补偿与回滚是两种不同层级的机制。回滚由存储引擎基于 undo 日志执行，发生在事务提交前，是物理层的确定性逆操作，不会失败，不需要业务代码参与。补偿由应用层业务代码执行，发生在事务提交后，是对已生效副作用的语义抵消；它本身会创建新的数据状态（如退款记录、取消状态），会失败，必须幂等、必须可重试。把补偿当回滚的典型错误是：补偿逻辑写成『删除刚才插入的行』。这会丢失审计痕迹，且一旦该行已被后续流程引用，删除会造成更严重的一致性破坏。补偿的正确形态是『把状态迁移到语义上等价于未发生的状态』。

误区二：『Saga 提供分布式原子性，所以是强一致』
Saga 只提供最终一致性，且明确牺牲隔离性（I）：T1..Tn 执行期间中间状态对外可见。更关键的是，Saga 的原子性不是确定性的——它依赖于『补偿最终必然成功』的假设。若补偿永久失败（如依赖服务永久不可用、业务规则阻止补偿执行），系统会永久停留在中间态，只能人工介入。这与数据库事务由存储引擎保证的原子性有本质区别：前者是应用层的收敛性保证，后者是物理层的确定性保证。

思考题：
一个三步 Saga：T1（创建订单）成功、T2（扣库存）成功、T3（扣款）失败，进入补偿路径。执行 C2（加回库存）时库存服务宕机，C2 失败。请回答：1) 此刻系统处于什么状态？2) Saga 框架依靠哪些机制最终收敛到一致？3) 若 C2 永久失败，Saga 是否还成立？为什么？——该题检验你是否真正理解：补偿的持久化与幂等重试、状态机在崩溃恢复中的作用，以及应用层语义补偿与存储引擎回滚在保证强度上的根本差异。
