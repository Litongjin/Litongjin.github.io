# 每日基础技术总结 · 2026-07-27 · 分布式事务的 Saga 补偿模式与隔离性缺陷

## 📚 今日主题

> **分布式事务的 Saga 补偿模式与隔离性缺陷**（架构与设计）

### 1. 核心概念速览
Saga 是一种面向长事务的分布式事务编排模式。其本质是：将一个全局事务拆解为多个本地 ACID 事务（正向步骤），并为每个正向步骤显式定义对应的补偿事务（Compensation）；执行时顺序提交正向步骤，任一步骤失败后，逆序执行已提交步骤的补偿事务，使业务状态回到语义等价于初始的状态。它解决的核心问题是在不引入分布式锁和两阶段提交（2PC）的前提下，协调跨服务、跨数据源的事务一致性，但代价是放弃原子性和隔离性，只提供最终一致性。
在计算机体系中的位置：它属于分布式系统一致性设计，是 CAP 定理中 AP 一侧、BASE 原则的落地手段。专业工程师必须掌握它，因为微服务架构下本地事务无法跨越服务边界，而 Saga 是处理此类场景的主流模式；同时，隔离性缺陷是模型固有矛盾，不理解它会导致设计出并发错误频发的系统。

### 2. 底层原理剖析
底层运行机制：
1. 全局事务 T 被拆分为 T1...Tn，每个 Ti 是独立本地事务，执行后立即提交，释放资源。
2. 每个 Ti 绑定一个补偿 Ci，Ci 必须幂等，且其业务效果能精确抵消 Ti 的提交效果。注意：补偿不是数据快照回滚，而是业务逻辑上的反向操作。
3. 编排器（或事件协同）顺序执行 Ti；若第 k 步失败，则从 k-1 逆序执行 C(k-1)...C1，完成回滚。若补偿也失败，则需重试、人工介入或对账。

隔离性缺陷的本质：Saga 不提供隔离级别，所有中间步骤的提交结果对其他事务可见。事务执行到 Ti 时，外部查询可以看到前 i 步已提交的局部状态。例如，订单已创建（T1 提交）但库存未扣（T2 尚未执行或失败），补偿未完成前，系统暴露了“已创建订单但未扣库存”的脏中间态。这相当于前端中异步操作多个状态更新但无原子提交，中间渲染结果可能被用户感知。

与前端已有概念的对比：Java 接口是编译期与运行期的显式契约，实现类必须 implements；TS 接口是编译期结构契约，只检查形状。Saga 的补偿操作类似于 Java 接口：必须显式编写并实现，系统不会隐式生成；而 2PC 的全局回滚类似于 TS 接口的结构匹配：只要底层数据库支持，系统自动完成，无需业务方显式定义。这个对比揭示了 Saga 对业务侵入性高的本质原因。

伪代码流程：
runSaga(steps) {
  executed = []
  for step in steps:
    try { await step.action(); executed.push(step) }
    catch {
      for i from executed.length-1 down to 0:
        await executed[i].compensate()
      throw
    }
}

### 3. 基础代码与实战验证
```text
以下为 TypeScript 编写的极简 Saga 编排器，演示正向执行与逆序补偿。代码不依赖任何框架，仅用 Promise 模拟异步边界。

interface SagaStep {
  name: string;
  action: () => Promise<void>;   // 正向本地事务
  compensate: () => Promise<void>; // 补偿事务，必须幂等
}

async function runSaga(steps: SagaStep[]): Promise<void> {
  const executed: SagaStep[] = [];

  for (const step of steps) {
    try {
      // 执行正向事务，例如：创建订单、扣库存、扣款
      await step.action();
      // 只有成功才记录，失败后用于逆序补偿
      executed.push(step);
    } catch (err) {
      // 补偿阶段：从最后一个成功步骤开始逆序调用补偿函数
      for (let i = executed.length - 1; i >= 0; i--) {
        // 补偿必须幂等，否则重复执行会破坏状态
        await executed[i].compensate();
      }
      throw err; // 向上层报告 Saga 失败
    }
  }
}

// 验证隔离性缺陷：假设 steps = [createOrder, deductStock, deductMoney]
// 在 createOrder 成功并推入 executed 后，另一个并发事务可能立刻读到新订单，
// 但库存尚未扣减，订单处于“已创建但未扣库存”的中间状态。
// 这就是 Saga 隔离性缺陷的直接表现，需要通过业务状态机或版本号来缓解。
```

### 4. 常见误区与进阶思考
误区1：认为 Saga 保证原子性。实际上 Saga 只保证最终一致性，且只有在所有补偿成功时才能回滚到初始状态。中间状态对其他事务完全可见，不能当成分布式 ACID 事务使用。
误区2：认为补偿操作是自动的、不会失败。补偿是业务逻辑，依赖网络与服务可用性；必须设计幂等、重试、超时和人工对账机制，否则补偿失败会导致系统永久不一致。

思考题：假设两个 Saga 并发执行：Saga A 从账户 X 转账 100 到 Y；Saga B 从 X 扣款 200 给 Z，X 初始余额为 150。两事务均先读余额再扣减，最终 X 余额可能变为 -150。在不使用数据库行锁和 2PC 的前提下，请设计一种基于状态机和版本号的业务级隔离方案，明确说明在哪个正向步骤中加入什么检查条件，以及如何通过补偿处理冲突，才能保证最终不出现负余额。
