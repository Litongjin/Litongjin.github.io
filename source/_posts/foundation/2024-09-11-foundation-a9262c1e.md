# 每日基础技术总结 · 2024-09-11 · 限流算法：令牌桶与漏桶的突发流量处理差异

## 📚 今日主题

> **限流算法：令牌桶与漏桶的突发流量处理差异**（架构与设计）

### 1. 核心概念速览
令牌桶（Token Bucket）与漏桶（Leaky Bucket）均为流量整形（Traffic Shaping）或速率限制（Rate Limiting）的核心算法，旨在保护后端服务免受突发流量冲击导致的服务降级或崩溃。本质区别在于对‘允许突发’的约束不同：令牌桶通过预存令牌允许一定程度的瞬时并发超过平均速率（平滑突发），适用于大多数需要兼顾吞吐与响应的前端至后端交互场景；漏桶则强制以恒定速率处理请求，无论输入流量如何波动，输出始终均匀，适用于严格限制最大并发处理能力的后端队列消费场景。掌握二者差异是设计高可用 API 网关、消息队列消费者及 AI 推理服务调度的基础。

### 2. 底层原理剖析
机制对比：
1. 令牌桶：维护一个容量为 C 的桶。系统以固定速率 r 向桶中生成令牌，直到满额。处理请求时需从桶中消耗 N 个令牌（通常 N=1）。若桶中有足够令牌则放行；若无则拒绝或排队。核心特征：允许‘借未来’，只要历史累积了令牌，即可瞬间消费，形成突发能力。
2. 漏桶：维护一个容量为 C 的队列/桶。请求进入桶中排队，系统以固定速率 r 从桶底漏水（处理请求）。若桶满，新到达的请求直接丢弃。核心特征：强制‘削峰填谷’，无论输入多么剧烈，输出速率恒定为 r，不产生任何突发。

前端类比：
- 令牌桶类似 Promise.allSettled + 信号量（Semaphore）：你可以在资源允许的极限内并行发起多个 I/O 操作，利用空闲期积累的能力爆发式完成。
- 漏桶类似严格的 Generator 或 Fiber 调度器中的固定时间片执行：无论有多少微任务堆积，调度器以固定的节奏逐个取出执行，保证 CPU 或主线程不被瞬间压垮，但延迟不确定性增加。

### 3. 基础代码与实战验证
```text
// 极简令牌桶实现 (Java风格伪代码)
class TokenBucket {
    private final int capacity; // 桶的最大容量
    private final double rate;  // 令牌生成速率 (tokens/sec)
    private double tokens;      // 当前令牌数
    private long lastTime;      // 上次更新令牌的时间戳

    public boolean tryAcquire(int permits) {
        long now = System.nanoTime(); // 获取当前高精度时间
        // 1. 计算自上次以来生成的新令牌数，并补充到桶中
        double newTokens = (now - lastTime) / 1e9 * rate;
        if (newTokens > 0) {
            this.tokens = Math.min(this.capacity, this.tokens + newTokens); // 上限截断
            this.lastTime = now;
        }
        // 2. 检查是否有足够的令牌
        if (this.tokens >= permits) {
            this.tokens -= permits; // 3. 扣除令牌，放行请求
            return true;
        }
        return false; // 4. 令牌不足，拒绝或阻塞
    }
}
// 关键点：令牌是在 'tryAcquire' 调用时动态累加的，因此即使长时间无请求，桶也会逐渐填满，从而支持后续的高突发。
```

### 4. 常见误区与进阶思考
误区 1：认为限流就是简单计数。许多初级开发者使用简单的计数器（Counter）做滑动窗口，但这无法处理时间粒度内的微观突发。令牌桶/漏桶的优势在于它们基于时间流速连续计算，而非离散切片，能更精准地反映真实的瞬时承载能力。

误区 2：混淆‘丢包’与‘排队’。在云原生架构中，漏桶通常对应着同步阻塞的缓冲队列，队满才丢包；而令牌桶常配合异步非阻塞模型，无令牌时直接返回错误（Fail-Fast），减少等待资源的浪费。选择哪种算法取决于系统是更能容忍延迟（排队）还是更能容忍失败率（丢弃）。

思考题：在分布式系统中，如果将‘令牌生成器’部署在各个应用实例本地（Local Token Bucket），相比集中式Redis令牌桶，它在 CAP 理论中牺牲了什么属性以换取什么性能优势？这种差异对 AI 大模型推理服务的高并发接入有何具体影响？
