# 每日基础技术总结 · 2026-07-27 · 限流算法：令牌桶与漏桶的突发流量处理差异

## 📚 今日主题

> **限流算法：令牌桶与漏桶的突发流量处理差异**（架构与设计）

### 1. 核心概念速览
令牌桶与漏桶是流量整形与速率限制的两种经典算法。令牌桶以恒定速率向桶中注入令牌，每个请求需消耗一个令牌，桶容量限制了可累积的令牌数，从而允许最大不超过桶容量的突发流量。漏桶以恒定速率从桶中漏水，请求先进入桶中，若桶满则丢弃，输出速率严格恒定。二者本质区别在于：令牌桶控制的是平均速率与突发上限，漏桶控制的是绝对平滑的输出速率。该机制位于分布式系统网关、API 网关、消息队列等基础设施层，是保障下游服务稳定性的基石。专业工程师必须理解其微观行为，才能正确配置参数，避免因突发导致雪崩或利用率下降。

### 2. 底层原理剖析
令牌桶：维护一个桶，容量为 C，当前令牌数为 T，令牌补充速率 r（每秒 r 个）。每来一个请求，若 T>=1 则取走一个令牌，放行；否则拒绝。补充过程可按时间增量模拟：每个时间单位 Δt，T = min(C, T + r*Δt)。关键：令牌可累积，因此若长时间空闲，桶被填满，紧接着可在瞬间消耗 C 个令牌，形成突发。漏桶：维护一个队列（桶），容量为 C，当前水量为 W，输出速率恒定 r（每秒 r 个）。请求到达时若 W<C 则加入队列，否则拒绝；调度器每秒从队列取出 r 个请求放行。关键：无论输入多不均匀，输出始终以速率 r 平滑进行，不会出现突发。对比前端已有概念：JS 的 throttle 函数（固定时间间隔执行）类似漏桶——每次事件后强制冷却，输出间隔均匀；而 debounce 则不同，它会把连续触发合并为一次，相当于不丢令牌但重置计时。更接近的类比是浏览器并发请求的调度器：若限制最大并发数为 N，相当于一个容量 N 的令牌桶（初始 N 个令牌，每个请求消耗一个，完成后归还一个），但这不是速率限制。令牌桶的补充速率与桶容量共同决定了短期突发量和长期平均速率；漏桶的队列容量决定了容忍输入尖峰的能力，但输出速率恒定。

### 3. 基础代码与实战验证
```text
极简 JS 实现验证差异：

class TokenBucket {
  constructor(rate, capacity) {
    this.rate = rate;        // 每秒补充令牌数
    this.capacity = capacity; // 桶容量
    this.tokens = capacity;   // 初始满桶，允许突发
    this.last = Date.now();   // 上次补充时间戳
  }
  take() {
    const now = Date.now();
    // 按时间差补充令牌，但不超过容量
    this.tokens = Math.min(this.capacity, this.tokens + (now - this.last) / 1000 * this.rate);
    this.last = now;
    if (this.tokens >= 1) {
      this.tokens -= 1;
      return true;
    }
    return false;
  }
}

class LeakyBucket {
  constructor(rate, capacity) {
    this.rate = rate;        // 每秒漏水速率，即输出速率
    this.capacity = capacity; // 桶容量，即队列长度
    this.water = 0;          // 当前水量
    this.last = Date.now();
  }
  take() {
    const now = Date.now();
    // 先按时间差漏水
    this.water = Math.max(0, this.water - (now - this.last) / 1000 * this.rate);
    this.last = now;
    if (this.water < this.capacity) {
      this.water += 1;
      return true;  // 入桶成功，等待调度输出
    }
    return false;   // 桶满，拒绝
  }
}

// 验证：令牌桶允许突发。rate=1/s, capacity=5，初始满桶，连续5个请求立即通过；之后需等待补充。
// 漏桶：rate=1/s, capacity=5，初始空桶，连续5个请求立即入桶，但输出速率仍为1/s，表现为请求被接受但实际执行被平滑。

注释：令牌桶的 take() 在请求时计算补充，漏桶的 take() 仅决定是否入桶，真正的输出由独立调度器按固定速率从队列取出。实际生产可用 setTimeout 或异步队列实现输出端。
```

### 4. 常见误区与进阶思考
误区1：认为令牌桶的速率就是瞬时速率。实际上令牌桶允许突发到桶容量，例如 rate=1/s, capacity=10，在空闲10秒后，可瞬间放行10个请求，瞬时速率远高于1/s。若误将 rate 当作硬性上限，会低估下游压力。误区2：漏桶的队列容量与令牌桶的桶容量混为一谈。令牌桶的桶容量控制的是可累积的突发量，漏桶的队列容量控制的是允许的输入尖峰缓冲，两者的语义完全不同。思考题：若令牌桶的 rate=1/s, capacity=10，桶已满，此时以10个/秒的速度持续输入请求10秒，然后停止。请描述这20秒内每个请求的通过时刻，并说明令牌桶与漏桶在此场景下行为差异的根本原因。
