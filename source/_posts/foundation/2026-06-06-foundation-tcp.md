# 每日基础技术总结 · 2026-06-06 · TCP 零窗口探测与接收窗口更新

## 📚 今日主题

> **TCP 零窗口探测与接收窗口更新**（网络基础）

### 1. 核心概念速览
TCP零窗口探测（Zero Window Probe）是TCP流控机制中处理接收窗口归零后恢复通信的可靠性保障。当接收方通告窗口为0时，发送方被禁止发送数据，但为了防止接收方后续发布的窗口更新（Window Update）报文丢失导致死锁，发送方启动持久计时器（Persist Timer），周期性发送包含1字节的探测报文，强制接收方回复当前窗口大小。本质是通过主动探询打破依赖单方向通知的失效链路，确保窗口状态信息最终一致。它解决的核心问题是：接收端缓存已满时，若其窗口更新通知在网络中丢失，发送端将永远等待，连接进入死锁状态。该机制属于TCP可靠传输与流量控制的交叉领域，是滑动窗口协议与ARQ思想的延伸。专业工程师必须掌握它，因为它是理解TCP拥塞控制、可靠传输、以及分布式系统背压机制的基础，也是排查网络故障和设计高性能传输协议（如QUIC）的底层参照。

### 2. 底层原理剖析
底层原理：TCP接收方通过ACK携带窗口字段通告剩余缓冲区容量。当应用层不消费数据，缓冲区填满，接收方通告零窗口。发送方在收到零窗口后停止发送，并设置持久计时器（通常初始1.5秒，指数退避至60秒）。计时器超时后，发送方发送一个特殊的零窗口探测包（ZWP），其序列号取当前发送队列中下一个未确认的序列号，但数据长度仅1字节（即使会暂时越过窗口，也允许）。接收方收到探测后，必须立即回复ACK，通告当前窗口值（可能仍为0，也可能已非零）。若窗口仍为0，发送方继续等待并再次探测；若窗口非零，发送方恢复正常发送。同时，接收方应用层腾出空间后，会主动发送窗口更新ACK（纯ACK，不含数据）。但纯ACK没有序号，可能被延迟或丢失，所以探测机制是最终兜底。伪代码状态机：
发送端：
  if (window == 0):
    启动持久计时器
    禁止发送数据
    超时后:
      发送1字节探测包(snd_nxt)
      重置计时器
      等待ACK
  收到ACK:
    更新window
    if (window > 0): 停止探测，恢复正常发送
接收端：
  收到数据包:
    若窗口为0但收到探测包:
      立即返回ACK(当前窗口)
    否则正常处理
  应用层读取数据后:
    若窗口从0变为非0:
      发送纯ACK通告新窗口

与前端ReadableStream背压的对比：
- 相似：都基于接收方反馈容量（desiredSize），发送方（生产者）据此暂停或恢复写入。
- 不同：TCP零窗口探测是网络协议层面对不可靠信道的补偿，主动探测解决通知丢失；前端流是内存模型，无丢包，靠Promise的pull信号精确同步，无需探测。这类似于Java接口与TypeScript接口的对比：两者都定义契约，但Java接口是编译期类型检查加运行时多态，TS接口是结构类型、擦除后无运行时存在——同样，TCP和前端流虽都实现背压，但底层机制和可靠性假设截然不同。

snd_una = 0      # 最早未确认序号

    global snd_una, window
    snd_una = max(snd_una, ack_no)
    window = new_window
    if window > 0:
        stop_persist_timer()
    else:
        # 窗口为零，启动持久计时器（若未启动）

    # 超时，发送1字节探测包，序号为snd_nxt
    send_probe(snd_nxt, data=b'\x00')
    # 重置计时器（指数退避）

def on_recv(segment):
    if segment.is_probe:  # 仅1字节数据且seq==snd_nxt

    else:
        # 正常处理，更新窗口
        if segment.len > 0:
            rcv_nxt += segment.len
        send_ack(rcv_nxt, window=current_available_space())

### 4. 常见误区与进阶思考
误区一：认为零窗口探测包携带的数据会突破流控，导致接收方缓冲区溢出。实际上探测包仅1字节，且接收方即使窗口为0也必须接收（序号匹配），但不会将其交付应用层，而是丢弃或缓存，并回复ACK通告窗口。这是协议允许的例外，目的是换取窗口状态的确定性。
误区二：认为只要接收方窗口更新（Window Update）发送成功，连接就能恢复，无需探测。但纯ACK可能因路由延迟或网络拥塞而丢失，且发送方无法区分是窗口未更新还是更新丢失。因此持久计时器是必须的兜底，不能依赖单向通知。
思考题：如果接收方在窗口为0期间收到探测包，但应用层同时刚好读取了数据、窗口变为非零，那么接收方回复的ACK中，ACK序号和窗口字段应该是什么？这个ACK能否同时作为对探测包的响应和窗口更新？请从TCP累积确认和窗口更新的角度解释，并说明这如何避免一次额外的窗口更新传输。
