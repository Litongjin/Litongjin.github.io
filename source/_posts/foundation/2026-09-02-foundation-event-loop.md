# 每日基础技术总结 · 2026-09-02 · Event Loop

## 📚 今日主题

> **Event Loop**（前端底层与计算机基础）

### 1. 核心概念速览
Event Loop（事件循环）是 JavaScript 运行时（浏览器、Node.js 等宿主环境）提供的并发执行模型，而不是 ECMAScript 语言规范的一部分。它的本质是一个永不退出的调度循环：当调用栈清空后，从宏任务队列（task queue）取出一个任务执行；执行完毕后再将微任务队列（microtask queue）清空；随后根据宿主规则决定是否更新渲染或进入下一轮循环。它解决的问题是：在单线程、非阻塞的约束下，如何让异步 I/O、定时器、用户事件、UI 渲染等任务有序交错执行。整个机制的底层基础是：JS 引擎（如 V8）只负责同步执行栈上的代码，本身没有任何等待能力；所有延迟动作都通过运行时把回调投入队列，由事件循环在合适的时机取出执行。
在计算机体系中的位置：事件循环位于 JS 引擎与操作系统之间——引擎负责执行表达式，宿主负责通过 libuv（Node）或 Web APIs（浏览器）发起异步系统调用，事件循环则是两者的协调器。它相当于用户态对操作系统线程调度的一种替代：OS 调度线程，事件循环在单线程内调度任务。
专业工程师必须掌握它，因为所有异步代码的执行顺序、性能瓶颈与死锁（饥饿）风险都由它决定；它是理解浏览器渲染管线、Node 的 I/O 模型、以及后续理解 Rust/Go 等语言的协程调度模型时的底层参照系。

### 2. 底层原理剖析
一、核心组件与职责划分
调用栈（Call Stack）：同步代码的执行场所，由 JS 引擎维护，后进先出。
宏任务队列（Task Queue / Macrotask Queue）：存放由宿主环境产生的回调，如 setTimeout、setInterval、I/O 事件、用户事件（浏览器）、setImmediate（Node）。每个任务被独立取出执行。
微任务队列（Microtask Queue）：存放 PromiseJobs，如 Promise.then/catch/finally 的回调、queueMicrotask、MutationObserver。它由 ECMAScript 规范中的 PromiseJobs 队列扩展而来，不属于宿主任务队列。
二、事件循环的精确流程（以浏览器 HTML 规范为参照）：
while (true) {
  1. 从宏任务队列取出最早的一个任务（task），执行其整个回调；
  2. 执行微任务检查点：反复取出微任务队列头部的任务执行；
     若微任务执行期间又注册了新的微任务，则继续清空，直至队列为空；
  3. 若当前是渲染时机（通常约 16.6ms 一帧），执行渲染步骤：style 计算 → layout → paint → 合成；
  4. 回到第 1 步。
}
关键点：微任务队列清空的时机是每个宏任务结束后、下一次渲染前，并且是把整个队列清空，而不是只清空一个。
三、Node.js 的差异
Node 的事件循环分为六个阶段：timers（定时器）→ pending callbacks（I/O 错误等）→ idle/prepare（内部）→ poll（获取 I/O 事件并执行回调）→ check（setImmediate）→ close callbacks（socket close 等）。每轮循环依次经过这些阶段；每个阶段有自己的任务队列。Node 11 之后，微任务队列会在每个回调执行完之后被清空，而不仅仅是每个阶段结束后；process.nextTick 回调则在本阶段与微任务检查点之间的中断点被优先清空（nextTick 队列优先级高于 Promise 微任务队列）。
四、与前端已有概念的对比
同一个术语接口在 Java（名义类型，必须显式 implements）与 TypeScript（结构化类型，只要形状匹配就兼容）中语义不同——Event Loop 在不同宿主中同样是同一个命名、不同实现细节：浏览器以任务加渲染帧为单位调度，Node 以阶段加回调为单位调度；但两者的共同骨架完全一致：单线程 + 调用栈清空后先清空微任务队列再取下一个宏任务。
此外，可以对比生成器函数与 async/await：生成器的下一次执行由外部手动调用 next() 驱动（调用者控制控制流），而 async/await 函数在 await 之后的恢复由事件循环的微任务队列自动调度（宿主控制控制流）。理解了这一点，就能明白 async/await 并不是把异步变同步，而是把异步回调包装成 Promise 微任务，在事件循环的固定时机恢复执行。

### 3. 基础代码与实战验证
```text
// 验证宏任务与微任务的调度次序（浏览器与 Node.js 通用）
const log = (msg) => console.log(msg);

log('1 同步代码：脚本开始执行');

setTimeout(() => {
  log('2 宏任务A：开始');
  Promise.resolve().then(() => {
    log('3 微任务B：由宏任务A注册');
  });
  setTimeout(() => {
    log('4 宏任务C：在宏任务A内部注册');
  }, 0);
  log('5 宏任务A：结束');
}, 0);

setTimeout(() => {
  log('6 宏任务D：第二个注册的宏任务');
}, 0);

log('7 同步代码：脚本执行完毕');

// 运行机制推演：
// 1. 同步代码依次执行：输出 1、7；
// 2. 事件循环从宏任务队列取出队首任务 A，入栈执行；
// 3. A 执行过程中注册了微任务 B 与宏任务 C；A 同步输出 2、5；
// 4. A 出栈后，立即执行微任务检查点，清空微任务队列：输出 3；
// 5. 事件循环取下一个宏任务。虽然 C 传入的是 0ms，但 0ms 只是最小延迟，
//    实际到期时刻由宿主时钟精度与钳制规则决定；且 C 注册时刻晚于 D，
//    所以当前轮次下一个宏任务仍是 D：输出 6；
// 6. 下一轮事件循环 timers 阶段，C 到期，输出 4。
//
// 最终输出顺序：1 → 7 → 2 → 5 → 3 → 6 → 4
// 关键结论：微任务队列的消费者是宏任务之间的间隙，而不是与宏任务并行的另一条流水线。
```

### 4. 常见误区与进阶思考
误区一：认为微任务一定先于宏任务执行，或者 Promise 比 setTimeout 快。
真相：微任务队列不是在宏任务之前，而是在每个宏任务结束之后、下一个宏任务开始之前被清空。同一轮里 Promise 回调确实看起来比 setTimeout 先执行，那是因为二者的入队目标不同、消费时机不同；但若某个宏任务内部注册了微任务，则微任务要等该宏任务结束后才执行。更隐蔽的后果是微任务饥饿（microtask starvation）：如果某个微任务不断注册新的微任务，事件循环会一直停留在清空微任务队列的步骤中，导致后续宏任务（定时器、I/O、用户事件）永远无法被取出，浏览器也因此无法进入渲染步骤，页面彻底卡死。
误区二：在 Node.js 中把 process.nextTick 当作 Promise 微任务。
真相：process.nextTick 不是 ECMAScript PromiseJobs 意义上的微任务，它是 Node 自有的 nextTickQueue，优先级高于 Promise 微任务队列；它在每个事件循环阶段之间甚至每个回调结束之后都会被检查并清空。因此同一段同步代码中注册的 nextTick 回调总是先于 Promise.then 执行。滥用 nextTick 会持续占用 CPU，使事件循环无法按预期进入 poll 阶段去等待 I/O，导致事件循环饥饿。
思考题：
在浏览器中，为什么递归调用 Promise.resolve().then(() => queueMicrotask(run)) 会导致页面完全失去响应，而递归调用 setTimeout(run, 0) 却不会？请结合整个 HTML 事件循环处理模型（宏任务 → 微任务检查点 → 渲染时机）说明两类队列在循环中的位置差异，并指出这个差异对使用 async 函数实现高频轮询或动画循环的工程启示。
