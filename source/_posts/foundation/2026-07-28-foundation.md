# 每日基础技术总结 · 2026-07-28 · 缓存穿透、击穿、雪崩的区分与布隆过滤器预热

## 📚 今日主题

> **缓存穿透、击穿、雪崩的区分与布隆过滤器预热**（架构与设计）

### 1. 核心概念速览
### 缓存穿透、击穿、雪崩的定义与本质

- **缓存穿透**：查询一个**数据库中不存在的数据**。由于缓存无法命中（因为根本没有对应数据），每次请求都会穿过缓存层直达存储层（如MySQL）。本质是缓存系统对“不存在”这一事实没有记忆，导致无效请求持续消耗数据库资源。
- **缓存击穿**：一个**热点key**在失效的瞬间，大量并发请求同时发现缓存未命中，全部回源数据库。本质是“单个key的缓存失效”与“高并发”在时间上重叠，导致瞬时压力集中。
- **缓存雪崩**：**大量key同时失效**（如批量设置相同过期时间）或缓存层整体不可用（如Redis宕机），导致所有请求流量全部倾泻到数据库。本质是缓存失效的**广度和时间叠加**，使数据库超出负载。

### 布隆过滤器预热

布隆过滤器是一种**概率性数据结构**，用于高效判断“一个元素**一定不存在**或**可能存在**”。预热指在系统启动时，将数据库全部已知存在的key预先放入布隆过滤器，作为缓存前的一道“哨兵”。当请求到来，先查布隆过滤器：若返回“不存在”，直接拒绝，不再穿透到数据库；若返回“可能存在”，才继续走缓存→数据库的链路。

### 在计算机体系中的位置

该知识点属于**分布式系统缓存架构**的核心问题，是设计高并发、高可用系统的基础设施之一。专业工程师必须掌握，因为它直接决定系统在极端流量下的稳定性，同时也是面试中区分“CRUD型工程师”与“架构型工程师”的经典考点。

### 2. 底层原理剖析
### 底层运行机制

缓存访问的标准逻辑（伪代码）：

```
function get(key):
    if bloomFilter.contains(key) == false:
        return null          # 一定不存在，拦截
    value = cache.get(key)
    if value == null:
        value = db.get(key)
        if value != null:
            cache.set(key, value)
    return value
```

- **穿透**：当key在数据库和缓存中都不存在时，布隆过滤器`contains`返回false，请求被直接拦截，数据库压力消失。
- **击穿**：热点key在布隆过滤器中“存在”，但缓存过期。此时大量并发同时查到缓存未命中，回源数据库。布隆过滤器无法解决此问题，需要引入**互斥锁**或**逻辑过期**。
- **雪崩**：大量key同时过期，布隆过滤器依然有效（它不依赖缓存），但缓存层整体失效导致流量直冲数据库。解决思路是**过期时间随机化**、**多级缓存**或**缓存集群高可用**。

### 布隆过滤器原理

布隆过滤器使用一个长度为m的位数组和k个独立的哈希函数。插入时，将元素经k个哈希函数映射到k个位置，置为1；查询时，检查这k个位置是否全为1。若任一位置为0，则元素**一定不存在**；若全为1，则**可能存在**（因为不同元素可能位重叠，造成误判）。其空间效率和查询时间均为O(k)，远优于存储全部key的Set结构。

### 与前端已有概念的对比

布隆过滤器与前端中常用的`Set`（如ES6的Set）都用于“成员存在性”判断，但本质区别如下：

| 维度 | Set | 布隆过滤器 |
|------|-----|-----------|
| 精确性 | 精确判断 | 概率性判断（有误判） |
| 删除 | 支持 | 不支持（除非用Counting Bloom Filter） |
| 空间 | 与元素数量线性增长 | 固定大小，与元素数量无关（但需预设） |
| 误判场景 | 无 | 可能把不存在的判为存在 |

这种“看似功能类似，但底层语义完全不同”的差异，类似于Java接口与TypeScript接口的区别：Java接口在运行时存在（可反射、动态代理），而TS接口在编译后完全擦除，仅在编译期做类型检查。两者名字相同，但本质和生命周期截然不同。理解这种差异，才能在实际架构中正确选型。

### 3. 基础代码与实战验证
### 极简验证：布隆过滤器预热 + 缓存穿透拦截

```python
class BloomFilter:
    def __init__(self, size, hash_fns):
        self.bits = [0] * size          # 位数组，初始全0
        self.hash_fns = hash_fns        # 多个哈希函数，每个返回整数

    def add(self, key):
        for fn in self.hash_fns:        # 遍历每个哈希函数
            idx = fn(key) % len(self.bits)  # 计算位索引
            self.bits[idx] = 1          # 置为1，表示该key可能存在

    def contains(self, key):
        for fn in self.hash_fns:        # 遍历每个哈希函数
            idx = fn(key) % len(self.bits)
            if self.bits[idx] == 0:     # 任一位置为0，则一定不存在
                return False
        return True                     # 所有位为1，可能存在（误判可能）

# 假设已有外部缓存和数据库对象
def preheat(bf, db_keys):
    """预热：将数据库所有已知key加入布隆过滤器"""
    for k in db_keys:
        bf.add(k)

def get(key):
    """缓存查询逻辑：布隆过滤器拦截穿透请求"""
    if not bf.contains(key):            # 过滤器判断“一定不存在”
        return None                     # 直接返回，不查询缓存和数据库
    value = cache.get(key)              # 查缓存
    if value is None:                   # 缓存未命中
        value = db.get(key)             # 回源数据库
        if value is not None:
            cache.set(key, value)       # 写回缓存，下次直接命中
    return value
```

**代码说明**：
- `BloomFilter` 的 `add` 和 `contains` 展示了位数组与多哈希的核心操作。
- `preheat` 模拟系统启动时，将数据库全部key预加载到布隆过滤器中，确保已知存在的key都能通过。
- `get` 函数中，第一步检查布隆过滤器，如果返回False，则请求被原地拦截，不会打到数据库，这就是“穿透”的解决方案。
- 该代码无法解决击穿和雪崩，因为这两个问题与“key存在但缓存失效”有关，布隆过滤器不涉及缓存生命周期管理。

### 4. 常见误区与进阶思考
### 常见误区

**误区1：把缓存穿透和击穿混为一谈**
穿透是“数据库里根本没有这条数据”，击穿是“数据库有这条数据，但缓存刚好失效”。两者都会导致回源，但本质不同：穿透是数据缺失，击穿是缓存缺失。布隆过滤器只能解决穿透，对击穿无效。若用布隆过滤器去应对击穿，等于用一个“存在性检查”去处理“时间点并发问题”，治标不治本。

**误区2：认为布隆过滤器可以动态增删，且无成本**
布隆过滤器不支持删除操作，因为删除一个key需要将其对应的位清0，但这可能影响其他key（哈希冲突重叠）。此外，如果数据库新增了key，必须同步更新布隆过滤器（否则会被误判为不存在），这需要一套“预热/增量更新”机制。很多工程师只看到布隆过滤器节省空间，却忽略了它的**不可删除**和**需要同步维护**的约束，导致实际落地时数据不一致。

### 深度思考题

假设布隆过滤器发生了误判：一个数据库中不存在的key，因哈希冲突所有位都被其他key置为1，导致过滤器返回“可能存在”，于是请求穿透到数据库。此时数据库返回空，但缓存和过滤器都不会记录这一“不存在”的事实，后续相同请求会持续穿透。请问：在不能增加数据库负担的前提下，你如何设计一个机制，既能利用布隆过滤器的低成本拦截，又能消除这种误判带来的重复穿透？
