# 每日基础技术总结 · 2026-07-18 · 栈帧布局与调用约定（x86-64 System V）

## 📚 今日主题

> **栈帧布局与调用约定（x86-64 System V）**（编程语言底层）

### 1. 核心概念速览
栈帧（Stack Frame）是程序运行时在调用栈上为单个函数调用分配的连续内存区域，其布局由目标架构的ABI（如x86-64 System V）规定。调用约定（Calling Convention）定义了函数调用时参数如何传递（寄存器/栈）、返回值如何存放、栈帧如何建立与销毁、以及哪些寄存器由调用方保存（caller-saved）或被调用方保存（callee-saved）。其本质是编译器和硬件之间关于过程抽象的契约，解决的是“如何安全地跳转执行并回传结果”这一底层控制流问题。在整个计算机体系中，它是编译原理、操作系统、调试器、逆向工程及性能剖析的基石。专业工程师必须掌握，因为任何高级语言（如C、Rust、Go）最终都编译为遵循该约定的机器码；理解栈帧布局能直接指导排查栈溢出、缓冲区溢出、栈回溯、尾调用优化失效等问题，也是理解异步编程中协程栈切换、JIT编译、无栈语言（如Go goroutine初始栈）的前提。

### 2. 底层原理剖析
x86-64 System V ABI的核心机制如下：
1. 参数传递：整数/指针参数依次使用RDI, RSI, RDX, RCX, R8, R9；浮点参数使用XMM0-XMM7；超出寄存器容量的参数按逆序压入栈（第7个及以后参数从右向左压栈）。返回值：整数在RAX，浮点在XMM0。
2. 栈帧结构：调用者执行CALL指令时，硬件将返回地址压入栈，RSP指向返回地址。被调用者通常执行`push %rbp`（保存调用者帧基址），`mov %rsp, %rbp`（建立新帧基址），然后`sub $N, %rsp`为局部变量和临时区分配空间。栈向低地址增长，局部变量在RBP负偏移处，被调用者保存的寄存器（RBX, RBP, R12-R15）压入栈后，RSP保持16字节对齐（CALL前RSP%16==8，进入函数后RSP%16==0，以便SIMD指令对齐访问）。
3. 寄存器保存职责：被调用者必须保存RBX, RBP, RSP, R12-R15（若使用则先压栈再恢复）；调用者保存RAX, RCX, RDX, RSI, RDI, R8-R11（无需保存，调用后可能被破坏）。
4. 红区（Red Zone）：在RSP下方的128字节区域为叶函数（不调用其他函数的函数）所有，编译器可将其用于局部变量而无需调整RSP，减少指令数。
5. 栈帧销毁：`leave`（等价于`mov %rbp, %rsp; pop %rbp`）恢复调用者帧，然后`ret`从栈顶弹出返回地址并跳转。
对比前端已有概念：Java的接口与TS的接口本质是类型契约，描述“能做什么”，属于编译期静态检查；而调用约定是运行时的二进制契约，描述“如何做”。前端中的函数调用是语言虚拟机（如V8的Ignition）解释执行的，栈帧由虚拟机管理（如JavaScript的调用栈存储执行上下文），而System V栈帧是CPU硬件与机器码层面的。二者相似之处在于都需管理参数传递、返回地址、局部变量作用域，但前端的“栈帧”更抽象（含词法环境、this绑定），不直接对应硬件寄存器。理解底层后能解释为什么JS函数调用开销远大于C，以及为什么尾调用优化在JS引擎中依赖调用栈的复用。

### 3. 基础代码与实战验证
以下为C代码及对应汇编，验证System V调用约定与栈帧布局。
```c
// test.c
long add3(long a, long b, long c) {
    long local = a + b;
    return local + c;
}
int main() {
    return (int)add3(1, 2, 3);
}
```
编译：`gcc -O0 -S test.c`（关闭优化以保留完整栈帧）。关键汇编（AT&T语法）及注释：
```
add3:
    pushq %rbp          # 保存调用者的RBP到栈，RSP-=8
    movq %rsp, %rbp     # 设置新帧基址RBP=RSP
    movq %rdi, -24(%rbp) # 参数a存入局部变量区（RBP-24）
    movq %rsi, -32(%rbp) # 参数b
    movq %rdx, -40(%rbp) # 参数c（前三个整数参数使用RDI,RSI,RDX）
    movq -24(%rbp), %rax # 加载a到RAX
    addq -32(%rbp), %rax # RAX = a+b
    movq %rax, -8(%rbp)  # 局部变量local存入RBP-8
    movq -8(%rbp), %rax  # 加载local
    addq -40(%rbp), %rax # RAX = local+c，返回值在RAX
    popq %rbp            # 恢复调用者的RBP，RSP+=8
    ret                  # 弹出返回地址到RIP，跳回调用处
main:
    pushq %rbp
    movq %rsp, %rbp
    movl $3, %edx        # 第三个参数放入RDX
    movl $2, %esi        # 第二个参数放入RSI
    movl $1, %edi        # 第一个参数放入RDI
    call add3            # CALL指令压入返回地址，然后跳转
    movl %eax, %eax      # 返回值RAX低32位赋给EAX（类型为int）
    popq %rbp
    ret
```
注意：-O0时参数可能从寄存器复制到栈，但传递仍遵循约定。若用`gcc -O2`，add3会被内联或优化为常量，栈帧消失，这正是编译器利用ABI进行优化的体现。验证红区：对叶函数，编译器可用RSP下方128字节而不调整RSP，例如`long f(long x){ return x+1; }`在-O2下直接`lea 0x1(%rdi), %rax; ret`，无栈帧。

### 4. 常见误区与进阶思考
误区1：认为栈帧总是包含RBP。现代编译器在优化级别（如-O2）下默认采用帧指针省略（-fomit-frame-pointer），RBP被当作通用寄存器使用，栈帧仅通过RSP访问，调试信息由DWARF提供。若误以为RBP始终是帧基址，会错误理解优化后的汇编。
误区2：混淆调用者保存与被调用者保存寄存器的实际含义。‘调用者保存’并非指调用者必须主动保存，而是指调用者需在调用后自行动手保存仍需的值；‘被调用者保存’指被调用者若使用这些寄存器必须先压栈保存，返回前恢复。如果只记住字面意义，容易在手动汇编或阅读反汇编时产生寄存器被覆盖的误判。
思考题：在x86-64 System V下，一个函数接受6个整数参数并递归调用自身，每次递归需要额外保存哪些寄存器？如果该函数是尾递归，编译器将其优化为循环，那么新的调用帧是否还在栈上分配？请结合寄存器保存规则和CALL指令行为解释，并说明这是否会导致栈溢出。
