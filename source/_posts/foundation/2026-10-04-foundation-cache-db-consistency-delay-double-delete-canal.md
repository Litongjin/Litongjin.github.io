# 每日基础技术总结 · 2026-10-04 · 缓存与数据库一致性：延迟双删与 Canal

## 📚 今日主题

> **缓存与数据库一致性：延迟双删与 Canal**（数据库与缓存进阶）

### 1. 核心概念速览
缓存与数据库一致性指缓存层与持久层在同一逻辑事务视图下的数据等价性，本质是解决多副本状态收敛问题。延迟双删是应用侧通过写后删缓存、延迟再删缓存来压缩并发读写导致的脏缓存窗口；Canal 是基于数据库 binlog 的变更数据捕获（CDC），将数据库作为唯一事实源，异步驱动缓存失效或刷新。它们分别代表主动补偿与事件驱动两类一致性实现路径，是分布式数据链路、后端高并发架构和 AI 在线特征服务必须掌握的基础。

### 2. 底层原理剖析
延迟双删运行机制：先删除缓存，再更新数据库，休眠 Δ 时间后再次删除缓存。第一次删除使读请求触发 cache miss 并回源数据库；第二次删除用于清除在数据库更新提交前由并发读请求写入的旧值缓存。其关键假设是 Δ 必须覆盖一次读请求从读取数据库到写入缓存的最大耗时，因此它是概率性收敛而非严格一致性。Canal 运行机制：伪装成 MySQL slave，向 master 发送 dump 请求，接收 binlog 事件，解析为结构化 row change，再投递给消费者执行缓存删除或更新。数据库提交日志是持久化顺序的权威来源，因此 Canal 将一致性责任从业务代码转移到日志消费链路。
与前端已有概念对比：TS 的 interface 是静态类型契约，编译后完全擦除，不产生运行时行为；Java 的 interface 是运行时类型系统的一部分，可参与多态分派、反射和 JVM 链接。类似地，延迟双删只是业务代码中的运行时补偿逻辑，没有全局事务边界；Canal 更像运行时元数据监听器，类似浏览器 MutationObserver 或 Node fs.watch，但数据源是数据库事务日志，具备持久化顺序与可重放性。

### 3. 基础代码与实战验证
```text
伪代码：延迟双删与 Canal 消费。

async function updateWithDelayDoubleDelete(id, payload) {
  await redis.del(key(id)); // 第一次删除：立即失效旧缓存，阻止后续读命中旧值。
  await db.update(id, payload); // 更新数据库：真正改变持久化状态，事务提交后 binlog 产生。
  await sleep(DELAY_MS); // 延迟窗口：覆盖并发读在数据库提交前读取旧值并回填缓存的时间。
  await redis.del(key(id)); // 第二次删除：清除并发读可能写回的旧值缓存。
}

Canal 消费端：
for (event of canalEvents) {
  if (event.type === 'UPDATE' && event.table === 'user') {
    redis.del(userKey(event.row.id)); // 基于 binlog 删除缓存：数据库提交顺序决定缓存失效顺序。
  }
}

关键边界：若第二次删除失败，需要重试队列或消息补偿；若 Canal 消费滞后，缓存仍会短期读到旧值。
```

### 4. 常见误区与进阶思考
误区一：把延迟双删当作强一致方案。它无法消除删除缓存与数据库提交之间的竞态，也不能处理删除失败后的持久补偿，只能降低脏缓存存活时间。误区二：认为 Canal 天然保证缓存最终一致。Canal 只保证捕获到已提交变更，消费端仍可能乱序、重复、失败，必须设计幂等删除、重试和位点恢复。
思考题：在『先更新数据库，再删除缓存』模式下，若缓存删除成功但消息通知丢失，延迟双删和 Canal 分别如何恢复？为什么基于 binlog 的方案比重试应用层删除更接近可靠事实源？
