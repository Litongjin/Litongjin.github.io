Redis 主从复制的全量重同步与部分重同步偏移量（架构与设计）

1. 核心概念速览

Redis 主从复制中的全量重同步与部分重同步偏移量，是主从节点间数据一致性协调的核心机制。全量重同步（Full Resynchronization）指从节点因初次连接或复制中断无法续传时，主节点生成当前数据集的完整 RDB 快照发送给从节点，并随后补发期间产生的写命令；部分重同步（Partial Resynchronization）则基于复制偏移量（Replication Offset）和复制积压缓冲区（Replication Backlog），使从节点在短暂断线后仅请求缺失的增量命令，避免全量传输。其本质是：通过主节点维护的连续字节流和从节点记录的消费位置，实现可断点续传的日志复制。该机制处于 Redis 高可用架构的数据同步层，是主从模式、哨兵模式、集群模式的基础设施，直接决定故障恢复的 RTO 和网络开销。专业工程师必须掌握，因为它涉及分布式系统中最关键的复制状态机设计、内存与网络资源权衡，以及故障场景下的行为预测，是排查复制延迟、脑裂、数据丢失等问题的底层知识。

2. 底层原理剖析

底层机制由三个核心状态构成：主节点维护的复制 ID（replid）、复制偏移量（master_repl_offset）和复制积压缓冲区（backlog）；从节点维护自身已复制的偏移量（slave_repl_offset）及上次同步的主节点 replid。当从节点发起 PSYNC 命令时，携带主节点 replid 和当前偏移量。主节点判断：(1) 若 replid 不匹配（如主节点重启或切换）则返回 +FULLRESYNC，触发全量重同步；(2) 若 replid 匹配但偏移量超出 backlog 范围（即所需增量已不在缓冲区）也返回 +FULLRESYNC；(3) 若偏移量落在 backlog 内，则返回 +CONTINUE，随后发送从偏移量到当前末尾的积压命令。全量重同步流程：主节点 fork 子进程生成 RDB 快照，同时将新写命令缓冲到 client 的 output buffer，快照发送完成后，将缓冲的命令以 RESP 协议流式发给从节点，从节点清空旧数据并加载 RDB，再执行增量命令，最终达到一致。部分重同步的偏移量本质是主节点发送的字节流累计位置，每个命令写入后 offset 增加，从节点每接收并执行一个命令也更新自己的 offset，网络传输中的命令在从节点侧可能乱序，但 Redis 通过 TCP 保证顺序，因此偏移量单调递增。对比前端概念：这类似于前端构建工具中的增量编译与全量编译——当文件 hash 未变时，增量更新依赖缓存；当缓存失效或 key 不匹配时，回退到全量重建。但更深层对比是浏览器 HTTP 缓存中的 ETag/If-None-Match：客户端通过 ETag 告知服务端资源版本，服务端若匹配则返回 304 表示未修改，否则返回完整资源。Redis 的部分重同步更像 HTTP 的 Range 请求——客户端知道已拥有的字节区间，请求缺失的部分，但 Redis 的缓冲区边界判断比 Range 更严格。另一个对比是 React 的调和（Reconciliation）与重新挂载（Remount）：key 不匹配时组件树整体重建，key 匹配时执行差异更新，这正是全量与部分同步的哲学。

4. 常见误区与进阶思考

误区一：认为部分重同步总是优于全量重同步，因此盲目调大 repl-backlog-size。实际上，部分重同步需要从节点偏移量恰好落在 backlog 内，若主节点写入速率极高，即使短时间内断线也可能导致溢出。而且 backlog 占用内存，过大会增加主节点内存压力，且积压数据在从节点追平后仍保留，造成无谓资源占用。应基于网络抖动概率、写入吞吐量和可接受的 RTO 动态调整。误区二：混淆复制偏移量与命令条数。偏移量是字节流累计长度，不是命令序号。一条多参数命令（如 MSET 或大 value）可能增加数百字节，而空命令或 PING 只增加几字节。从节点在部分重同步时，主节点发送的是从偏移量开始的原始字节流，从节点直接解析执行，因此必须保证主从的复制协议版本一致。思考题：假设主节点 A 在 t1 时刻写入命令 X（offset=100），此时从节点 B 已同步到 offset=80。t2 时刻 B 断线，主节点继续写入命令 Y（offset=120），同时主节点执行了 REPLICAOF NO ONE 变成独立节点（replid 变化），随后又执行 REPLICAOF 127.0.0.1 A 重新挂回。问：B 重连时，A 能否部分重同步？为什么？如果不能，A 会如何响应？请从 replid 和 backlog 两个条件分别分析。
