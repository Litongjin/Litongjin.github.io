JavaScript BigInt 与 Number 的精度边界：IEEE 754 双精度浮点数陷阱（前端底层与计算机基础）

1. 核心概念速览

定义

  • Number：ECMAScript 的 Numeric 类型之一，语义等价于 IEEE 754-2019 的 binary64（双精度浮点）。64 bit 布局：s(1) | e(11) | f(52)，指数采用 bias=1023 的移码，规格化数隐含前导 1，故有效精度为 53 bit（1 隐式 + 52 显式）。
  • 安全整数边界：|n| <= 2^53 - 1（Number.MAX_SAFE_INTEGER = 9007199254740991）时，区间内任意两个相邻整数映射到不同的 double，整数域与 double 域在该区间双射。越过该边界后 ULP（unit in the last place）从 1 跳到 2 并继续倍增，整数域出现空洞：”可表示”不再等于”可区分”。
  • BigInt（ES2020）：任意精度二进制整数，符号 + 幅值表示，无溢出、无舍入误差；typeof 1n === 'bigint'，是原始类型而非 Number 的包装对象（new BigInt() 抛 TypeError）。与 Number 之间不存在任何隐式转换，混合算术直接抛 TypeError。

解决什么问题

  • Number 解决的是”以固定 64 bit 逼近实数（含极大/极小量级、含小数）”的问题，代价是有限精度 + 舍入；
  • BigInt 解决的是”整数域内精确、无溢出运算”的问题，代价是任意精度带来的堆分配与慢路径运算，且不覆盖小数。
  • 二者是互补而非替代关系：需要精确整数语义时必须退出浮点域，需要小数与量级时必须留在浮点域（并按定点/整数化策略规避误差）。

在整个体系中的位置

IEEE 754 是所有主流运行时的公共数值底座：JS Number、Java double、C double、Python float、数据库 double precision、GPU 的 FP32/FP64、以及 PyTorch/TensorFlow 的 float32/float64/float16/bfloat16 全部沿用同一套位布局与舍入规则。因此本知识点不是”JS 的一个坑”，而是浮点数值语义的入口。

为什么专业工程师必须掌握

  1. 跨语言数据一致性：snowflake ID、数据库 BIGINT、Kafka/Protobuf int64 一旦经 JSON.parse 进入 JS，末尾数字会被静默改写，链路任何一环都可能丢数据。
  2. 协议边界：JSON 只有一种数字类型（无 int64/long 区分），序列化层的类型信息必须由 IDL 或字符串承载来补齐，这是接口契约设计问题。
  3. AI/数值计算：FP16/BF16 累加、loss scaling、梯度求和顺序敏感性、float32 下的 epsilon 选择，本质都是同一套 ULP 与舍入机制的直接后果。
  4. 性能与语义权衡：BigInt 走运行时堆路径无法被 JIT 内联为机器字运算，在热点路径上使用会带来数量级的开销差异。

4. 常见误区与进阶思考

误区一：混淆”可精确表示”与”可安全还原”

常见错误认知是”只要 Number.isInteger(x) 为 true，就说明这个整数没丢精度”。事实上任何 |n| > 2^53 - 1 的整数只要进入 Number 域，失真就在赋值/解析那一刻已经发生，此后所有检测（isInteger、toFixed、Math.round）都只是在已损坏的值上做判断。典型事故链：后端 BIGINT 主键 → JSON 序列化（合法）→ JSON.parse（静默改写末位）→ 前端回传 → 更新到错误记录。整个过程无任何异常抛出。

根因在于 JSON 规范只有一种 number 类型，不含 int64/long 概念，因此类型信息必须由传输格式或 IDL 承载，不能由 JSON 数字承载。正确做法是在协议层把 64 bit 整数强制声明为 string，或在解析器层面（词法阶段保留原始 token）以 BigInt 重建；仅在 parse 的 reviver 里做转换是不够的，因为 reviver 拿到的 v 已经是 Number。

误区二：把 BigInt 当作 Number 的”更精确版本”无差别替换

BigInt 与 Number 在规范层面是三处不兼容的：

  1. 禁止隐式转换：1n + 1 抛 TypeError，这是刻意的设计决策——避免 BigInt 转 Number 时静默丢精度，也避免 Number 转 BigInt 时对非整数抛错。因此在 API 边界上必须显式收敛类型，类型体操（TS 无法区分 number 与 bigint 的运算重载）也会随之放大。
  2. 语义差异：BigInt 除法是向零截断，而 Number 的除法是精确商再舍入；5n / 2n === 2n，而 5 / 2 === 2.5。迁移金额计算逻辑时，舍入策略必须从”就近取偶”改为显式的余数处理（(a * scale + b / 2n) / b 之类的手工四舍五入）。
  3. 生态不可用：Math.*、Date、JSON.stringify、TypedArray（除 BigInt64Array/BigUint64Array）均不接收 BigInt；且 BigInt 每次算术都会分配 HeapObject，无法被 JIT 内联为机器字指令，在热路径中相对 Number 有数量级开销差，同时把精度问题转化成 GC 压力问题。

补充一点易被忽略的：Number(2n ** 60n) 这类显式转换不会抛错，会静默产出失真的 double。显式转换存在，就意味着”禁止隐式转换”并不等于”安全”。

思考题

2^53 本身可以被 binary64 精确表示，为什么 Number.isSafeInteger(2 ** 53) 仍然返回 false？请从 Number 域的”可逆性”定义出发，结合 ULP 与 roundTiesToEven，说明：

  • 在 [2^52, 2^53) 与 [2^53, 2^54) 两个区间内，整数到 double 的映射分别是单射还是多对一？
  • 若一个 double 的数学值 v 落在 [2^53, 2^54)，仅凭 v 能否唯一确定用户原本输入的整数？
  • 由此推广：为什么 Number.isSafeInteger 的判据是 |n| <= 2^53 - 1 而不是 |n| <= 2^53，并且为什么这个界与”有效精度 53 bit”是同一件事的两种表述？
