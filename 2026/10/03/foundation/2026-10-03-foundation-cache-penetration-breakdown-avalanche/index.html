缓存穿透、击穿、雪崩与解决方案（数据库与缓存进阶）

1. 核心概念速览

缓存穿透、击穿、雪崩是分布式缓存（典型如 Redis）在极端或异常流量下面临的三类失效问题，本质上是「缓存未命中」与「缓存失效」在不同粒度、不同时机下的系统性放大。

  • 缓存穿透：查询一个必然不存在的数据，导致请求直达存储层（DB），缓存形同虚设。本质是「缓存未命中集合」无法被缓存本身消除，因为不存在的数据没有可缓存的副本。
  • 缓存击穿：某个热点 key 在过期瞬间被大量并发请求同时访问，所有请求穿透到 DB。本质是「单个 key 的失效」与「并发读放大」的叠加。
  • 缓存雪崩：大量 key 在同一时间窗口集中过期，或缓存节点整体宕机，导致请求洪峰直达 DB。本质是「失效的全局同步性」或「可用性缺失」引发的流量瞬间击穿底层存储。

解决方案各自针对本质：穿透用「空值缓存」或「布隆过滤器」在缓存层拦截必然不存在的数据；击穿用「互斥锁」或「逻辑过期」保证并发下只有一个请求回源；雪崩用「过期时间加随机扰动」打散失效窗口，或用「多级缓存」「高可用集群」避免单点容灾。

该知识点处于「存储体系的分层架构」中，位于缓存与数据库之间的一致性、可用性与极端流量防护边界。专业工程师必须掌握，因为它是构建高并发读服务的基础防线，直接决定系统在流量尖峰下的可用性；同时它也是理解「缓存一致性」「分布式锁」「限流降级」等进阶话题的起点。

2. 底层原理剖析

底层机制可从「缓存的工作模型」推导：缓存是 key-value 的短期存储，命中则返回，未命中则回源并回填。三类问题均是该模型在特定输入分布和失效时序下的退化。

穿透的底层本质：对不存在 key，回源查询 DB 后仍无结果，无法回填；因此每次相同查询都会重复回源。布隆过滤器利用「位数组 + k 个哈希函数」对 key 做存在性预判，若判断不存在则一定不存在（零漏报），直接拦截；若判断存在则可能误判，则放行到缓存/DB。空值缓存则将「不存在」本身作为结果缓存，TTL 设短，以空间换 DB 压力。

击穿的底层本质：热点 key 过期瞬间，缓存中无值，多个请求同时发现未命中。互斥锁方案（Mutex）保证只有一个请求持有锁并回源 DB，其余请求等待锁释放后直接读取缓存；可用 SETNX 或分布式锁实现。逻辑过期方案不设置物理 TTL，而是存一个逻辑过期时间戳；读取时若发现逻辑过期，则先返回旧值，同时异步一个线程去回源并更新缓存，避免同步阻塞所有请求。

雪崩的底层本质：大量 key 的 TTL 相同或集中在同一时刻，导致缓存失效窗口重叠，DB 请求数量呈数量级跃升。解决：TTL 加上随机偏差（如 base + rand(0,300)s），使失效时间均匀分布；或引入多级缓存（L1 本地缓存 + L2 分布式缓存），L1 失效后仍命中 L2；或缓存节点用哨兵/集群保证高可用，避免整体宕机。

与前端知识体系的对比：类似于前端浏览器 HTTP 缓存中的「强制缓存」与「协商缓存」——缓存穿透可类比「请求一个从未存在的资源」，浏览器无法缓存 404，因此每次都要回源；缓存击穿可类比「某个 JS/CSS 文件刚好过期，页面并发加载同一资源」，此时浏览器会并发发起多个请求，但浏览器有 Cache-Control 和启发式算法，且前端服务通常有 bundler 的 content hash 保证资源不变性，所以少遇此类问题；缓存雪崩可类比「站点发布导致静态资源全部替换 CDN 缓存危险期」，或「多个图片同时过期引发回源风暴」。底层机制一致，区别在后端需处理高频动态数据下的并发一致性。

4. 常见误区与进阶思考

误区一：把缓存穿透和击穿混为一谈，用随机 TTL 解决穿透。 随机 TTL 只对雪崩有效，穿透是「数据不存在」，与 TTL 无关；必须用空值缓存或布隆过滤器。同理，互斥锁能防击穿但不能防穿透，因为锁只能限流，无法拦截必然不存在的请求。

误区二：认为布隆过滤器是完美的存在性判断。 布隆过滤器有误判率（false positive），即判断存在时可能不存在，会放行少量请求到 DB；但判断不存在时一定不存在，因此它能消除穿透的绝大多数流量。若业务要求绝对无穿透，需配合空值缓存或更精确的结构（如 Cuckoo Filter 支持删除）。

进阶思考题： 假设缓存 key 的 TTL 为 10 秒，DB 数据每 6 秒更新一次。在「逻辑过期」方案中，异步回源更新缓存时，若 DB 更新与缓存写入之间存在竞态，如何保证读取到的是新数据？请从「读写顺序」「版本号」或「双写」角度，设计一个可以容忍短暂不一致但不能脏读的更新协议。
