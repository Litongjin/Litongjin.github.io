令牌桶与漏桶限流：平滑性对比与 Redis 实现（后端基础）

1. 核心概念速览

令牌桶（Token Bucket）与漏桶（Leaky Bucket）是两种经典的流量整形与速率限制算法，属于网络流量控制与分布式系统保护中的基础机制。令牌桶的本质是一个以固定速率生成令牌、并以容量为上限的桶；请求必须消耗一个令牌才被允许通过，否则被拒绝或等待。漏桶的本质是一个以固定速率出水的队列；请求进入桶中，若桶已满则溢出（拒绝），否则按恒定速率被处理。两者解决的核心问题是：在突发流量与稳定速率之间取得可配置的折中——令牌桶允许一定程度的突发（受桶容量限制），而漏桶强制完全平滑的输出（输出速率恒定不变）。在计算机体系中的位置：位于应用层与网络层之间的中间件/网关/服务治理层，属于限流（Rate Limiting）与背压（Backpressure）机制的基石。专业工程师必须掌握它，因为它是高并发系统、微服务治理、API 网关、消息队列消费者等场景下保护后端服务免受流量尖峰冲击的底层原语，且直接影响系统的可用性与稳定性。掌握其数学本质与实现细节，才能正确选择算法并避免在生产环境中的隐性缺陷。

2. 底层原理剖析

令牌桶的底层运行机制：系统以每秒 r 个令牌的速率向桶中补充令牌，桶的最大容量为 b（即 burst 上限）。每次请求到达时，如果桶中令牌数 ≥ 1，则取走一个令牌并放行；否则请求被限流（可拒绝或等待）。实现上通常不采用真实的定时器逐秒添加令牌，而是使用‘惰性计算’：记录上次补充令牌的时间戳 lastRefillTime，当前可用令牌数 storedTokens，在请求到达时计算 (now - lastRefillTime) * r 得到应补充的令牌数，累加至 storedTokens（上限为 b），然后判断是否放行。这样避免了后台线程，时间复杂度 O(1)。令牌桶的平滑性特点：输出速率在长期平均为 r，但允许在空闲后积累 b 个令牌，从而支持短时突发流量（burst），突发长度最大为 b 个请求。漏桶的底层运行机制：维护一个固定容量为 c 的队列（或计数器），请求到达时如果队列未满则入队，否则拒绝；后台以固定速率 f 从队列中取出请求进行处理（或通过计时器控制每 1/f 秒放行一个）。漏桶的输出速率严格恒定，与输入无关，平滑性最强，但无法应对突发，任何突发都会被排队或丢弃。与前端已有概念的对比：令牌桶类似于前端并发控制中的信号量（Semaphore）但带有时间维度——信号量只限制同时执行的并发数，令牌桶同时限制速率和突发；漏桶类似于前端任务队列中的‘串行执行器’（如 RxJS 的 concatMap），强制每个任务按固定间隔执行，但 concatMap 不提供容量溢出丢弃的语义。更本质地，令牌桶是‘速率 + 容量’的双参数模型，漏桶是‘容量 + 恒定处理速率’的单速率模型。在 Redis 实现中，令牌桶利用 Lua 脚本保证原子性，避免多实例并发下的竞态；漏桶则可以用计数器记录当前桶中积压量，配合时间戳计算应放行的数量，同样以 Lua 脚本实现。

4. 常见误区与进阶思考

误区一：认为令牌桶的‘速率’就是‘每秒最多通过的请求数’。实际上令牌桶的速率 r 是长期平均速率，而桶容量 b 允许瞬时超过 r 的突发，因此峰值速率可以远高于 r（只要 burst 长度 ≤ b）。生产环境常见错误是设置 r=100, b=100，结果在突发流量下瞬间放行 100 个请求，远超下游预期。必须根据下游的真实承载能力同时设置 r 和 b，而不是只看 r。
误区二：在 Redis 限流中忽略原子性，使用 get + 计算 + set 的步骤完成，导致多实例并发下同一瞬间多个请求都读到相同令牌数而全部放行，突破限流上限。正确实现必须使用 Lua 脚本或事务，保证检查与更新的原子性。
思考题：假设令牌桶参数为 r=10 桶/秒，b=20，当前桶中已有 15 个令牌，且已有 0.5 秒没有请求。此时连续到达 18 个请求，请问第 18 个请求是否会被放行？请结合惰性补充公式计算，并说明如果此时使用漏桶（容量 20，出速 10/秒）结果有何不同——这个对比能检验你是否真正理解两种算法对突发与平滑性的本质差异。
