每日基础技术总结 · 2026-08-28 · 进程与线程的区别

📚 今日主题

进程与线程的区别（后端基础（Node.js / Java / Python））

1. 核心概念速览

定义

进程（Process）是操作系统用于资源分配的基本单位：它封装了一个完整的虚拟地址空间（代码段、数据段、堆、栈、mmap 映射区）以及文件描述符表、信号处理器、工作目录、用户凭据等内核资源。线程（Thread）是操作系统用于 CPU 调度的基本单位：它是进程内部的一条独立执行流，拥有私有的硬件执行上下文（程序计数器、通用寄存器、栈指针、浮点/向量寄存器、内核栈）与线程局部存储，但与同进程的其他线程共享整个地址空间与文件资源。

本质机制

  • 进程之间虚拟地址空间相互隔离：普通代码无法直接读写另一进程的内存，只能通过内核提供的 IPC（管道、消息队列、共享内存、mmap）协作。隔离正是故障隔离与安全边界的来源。
  • 同进程内线程之间虚拟地址空间完全共享：任意线程都能读写同一进程的堆对象与全局数据（甚至对方的栈）。共享带来零拷贝的数据交换，但引入数据竞争（data race）与内存可见性问题。

解决的问题

进程解决「资源隔离 + 系统内多任务」；线程解决「在同一隔离边界内实现轻量级并发」。若用多进程实现进程内部并发，每次切换都需要换页表、刷 TLB、冷化 cache，代价极高；线程复用地址空间，切换只换执行上下文，成本低一个量级。

体系位置与必要性

操作系统内核（调度器与内存管理器）是全部并发理论的地基。上层模型——Java 的 ThreadPoolExecutor、Go 的 goroutine（M:N 调度于 OS 线程之上）、Node.js 的 worker_threads、Python 的 threading/asyncio——本质都是「用户态调度」与「内核态调度」的组合与封装。AI 领域多卡训练与分布式参数服务器同样建立在进程/线程与共享内存/IPC 之上。不掌握这层机制，就无法解释为何 goroutine 可到百万级而 OS 线程通常只有数千，也无法定位死锁、数据竞争、伪共享（false sharing）等线上疑难问题。

2. 底层原理剖析

内核视角

Linux 中每个进程对应一个 task_struct（进程控制块），其内存布局由 mm_struct 描述（含页表根指针）。创建线程的本质是 clone() 一个带 CLONE_VM、CLONE_FILES、CLONE_FS 标志的 task_struct：多个 task 共享同一个 mm_struct 与 files_struct。因此「线程是轻量级进程」的准确含义是：线程是「地址空间共享的 task」。

线程独有 vs 进程共享

  • 线程独有：寄存器上下文（thread_struct）、调用栈（在共享地址空间中分配的私有栈区）、内核栈、信号掩码、errno、线程局部存储（TLS）。
  • 同进程线程共享：页表与虚拟地址空间、文件描述符表、工作目录、umask、信号处理函数。进程切换则以上全部隔离。

上下文切换完整路径（x86-64 + Linux）

用户态执行 → 中断/系统调用/异常 → CPU 陷入内核态 → 保存当前线程的通用寄存器、RSP、RIP、FPU/向量状态到其 TCB → 内核调度器选出下一任务 → 若与当前线程属于同一进程，直接恢复新线程的寄存器与内核栈并返回用户态；若属于不同进程，还需执行 switch_mm_irqs_off()：写入新进程页表基址到 CR3，并使 TLB 中属于旧地址空间的映射失效（现代 CPU 用 PCID 优化）。进程切换还会让 L1/L2 缓存中的代码与数据热块失去命中意义，线程切换则保留缓存温度。

成本量级（相对关系比绝对值更重要）

  • 用户态协程切换（仅保存若干寄存器、不陷入内核）：约几十 ns。
  • 同进程线程切换：约 1–5 µs，必须进入内核、经过调度器、操作运行队列锁。
  • 进程切换：在以上基础上叠加 CR3 切换、TLB 失效与 cache 冷启动，可达几十 µs。

与前端已有知识的对照

  • 浏览器多进程架构：每个 tab/iframe 通常是独立进程；渲染进程内部的主线程、合成器线程、Worker 线程共享该渲染进程地址空间，这才是真正的「线程」。前端日常写的 Promise/async/await 只是单线程事件循环上的任务调度，根本不是并发执行单元。
  • Web Worker 默认模型是「独立 JS 堆 + postMessage 结构化克隆」：数据被复制/转移，Worker 之间不能直接改写对方内存，除非显式使用 SharedArrayBuffer + Atomics。它在语义上更接近 OS 进程间 IPC（共享内存 + 同步原语），而非传统共享一切内存的线程。这也是前端工程师天然习惯无数据竞争并发的原因。
  • 同名异质的警示可类比「Java 接口是运行期类类型契约，TS 接口是编译期结构类型约束」：同叫 interface，底层语义层级完全不同。Java 的 Thread 是 1:1 内核线程，synchronized/volatile 语义由 JMM（Java 内存模型）定义；JavaScript 的 async 甚至不是线程。带着前端心智写后端并发，是多数线上 bug 的来源。

4. 常见误区与进阶思考

误区一：线程切换「只是保存几个寄存器」，所以很便宜

寄存器保存/恢复只是完整路径的一小段。线程切换的实际代价是：用户态 → 内核态（异常/系统调用入口）→ 调度器（关抢占、运行队列自旋锁、可能的负载均衡）→ 恢复上下文 → 回到用户态。用户态协程（goroutine、协程）之所以快，是因为切换在运行时内完成，不陷入内核；但协程一旦阻塞在系统调用或参与内核级抢占，仍会映射到 OS 线程切换。把「协程」与「线程」的成本混为一谈，是并发性能预估失准的常见根源。此外对同一进程内的多线程而言，即使不切换进程，多核同时在运行队列自旋锁上争用也会成为可扩展性瓶颈。

误区二：共享内存免拷贝 = 高效，所以线程通信不用设计

共享内存只消除了数据拷贝，但引入了缓存一致性开销。多核同时写同一 cache line 时，MESI 协议会让该缓存行在多个核的私有 L1 之间反复作废与重载（cache line ping-pong），这就是伪共享（false sharing）让多线程比单线程更慢的原因。共享数据必须配合同步原语（互斥锁 / 原子 RMW 指令 / 内存屏障）并显式约定内存顺序，否则轻则结果错误，重则不可复现崩溃。前端 postMessage 的拷贝模型天然规避了这些，代价是序列化开销——这正是两种并发模型之间本质的 trade-off。

思考题

在 x86-64 多核 CPU 上，同一进程的两个线程在两个核上同时执行机器指令 addl $1, counter（counter 是共享内存变量）。请从三层分析：

  1. 单核场景下，这条指令还需要加锁吗？（提示：中断只发生在指令边界，单条指令在单核上天然原子）
  2. 多核场景下，即使两个核各自「原子」执行完这条指令，为什么仍可能丢失一次更新？（提示：L1 cache 是每核私有的，两个核可能同时持有 counter 的旧值副本）
  3. 给指令加上 lock 前缀后，硬件层面究竟锁住了什么？（深入思考：是锁总线，还是锁 cache line 的 MESI 状态，还是二者兼有？回答到这一层，才说明你真正理解了共享内存的硬件代价）
