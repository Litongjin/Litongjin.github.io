最长递增子序列的 O(n log n) 贪心二分（算法与数据结构）

1. 核心概念速览

最长递增子序列（LIS）问题：给定一个序列，求其中严格递增的子序列的最大长度。O(n log n) 贪心二分算法的本质是维护一个数组 tails，其中 tails[i] 表示所有长度为 i+1 的递增子序列的最小末尾元素。遍历原序列时，对每个元素 x，在 tails 中二分查找第一个不小于 x 的位置，若存在则替换，若不存在则追加。该操作利用了 tails 的严格单调递增性，将动态规划状态转移的复杂度从 O(n^2) 降为 O(n log n)。它属于算法设计中“贪心+二分”的经典范式，也是动态规划中“状态优化”的代表。在计算机体系中，它广泛用于 diff 算法、基因序列比对、AI 中的序列建模等场景；专业工程师必须掌握，因为它是理解前端框架（如 Vue 3 的 diff 优化）和高效处理序列问题的底层基础。

2. 底层原理剖析

底层机制：tails 数组的长度 len 表示当前已知的 LIS 长度，但 tails 本身不一定是 LIS。遍历每个 x，需要找到 tails 中第一个大于等于 x 的位置 pos（即 lower_bound）。由于 tails 严格递增，可以二分查找。若 pos == len，则说明 x 大于当前所有尾部，可以接在任何一个子序列后面，因此 LIS 长度加一，将 x 追加到尾部；否则用 x 替换 tails[pos]，这意味着长度为 pos+1 的递增子序列的末尾被更新为一个更小的值，从而增大了该长度子序列继续扩展的潜力。替换后 tails 依然严格递增：因为 pos 是第一个 >=x 的位置，所以 tails[pos-1] < x（若 pos>0），且 x <= 原 tails[pos] < tails[pos+1]（若 pos<len-1）。该算法的贪心性体现在：总是用更小的末尾替换当前末尾，使得未来元素更容易接上。

与前端已有概念的对比：Vue 3 的 patchKeyedChildren 中，为了最小化 DOM 移动，会对新旧子节点的索引数组求解 LIS，以确定哪些节点不需要移动。Vue 内部实现的就是这个贪心二分算法，但为了拿到具体的子序列索引，需要在替换时记录每个元素的前驱（predecessor），最后回溯得到 LIS。这里仅求长度则无需前驱。这与“Java 接口与 TS 接口”的对比类似：二者表面都在处理“序列”概念，但一个只求长度，一个需要完整序列；一个直接操作数值，一个操作对象索引。另外，前端工程师常用的二分查找是在静态有序数组上查询目标值，而这里的二分查找是在动态构建的有序数组上维护“最小末尾”，返回值是插入位置而非目标值。理解这种差异，能避免在应用算法时产生迁移错误。

4. 常见误区与进阶思考

常见误区：

  1. 误以为 tails 就是最终的最长递增子序列。实际上 tails 只记录各长度子序列的最小末尾，它本身不一定构成一个递增子序列。例如序列 [2,3,4,1]，遍历后 tails 变为 [1,3,4]，长度为 3，但 LIS 是 [2,3,4]，tails 并不是原始序列的子序列。
  2. 误以为该算法可以直接输出 LIS 序列。贪心二分只保证长度正确，若需要具体序列，必须在每次替换/追加时记录该元素在 tails 中的位置及前驱，最后从最后一个元素回溯。Vue 3 的 diff 正是这么做的。

进阶思考题：如果要求的是最长不下降子序列（允许相等元素），算法应如何改动？为什么严格递增时二分条件用“第一个 >= x”而不是“第一个 > x”？请用序列 [2,2] 推演说明错误原因。
