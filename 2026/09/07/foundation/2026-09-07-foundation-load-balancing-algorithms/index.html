负载均衡算法对比：轮询、加权轮询与最小连接数的适用场景（网络基础）

1. 核心概念速览

负载均衡算法是分布式系统中将请求分发到后端服务节点的策略集合，其本质是在多个可用资源之间做路径选择，以达成吞吐量最大化、延迟最小化或资源利用率均衡等目标。轮询（Round Robin）、加权轮询（Weighted Round Robin）与最小连接数（Least Connections）分别对应不同维度的调度决策：轮询基于位置的无状态循环，加权轮询在位置基础上引入静态权重，最小连接数则基于后端实时并发量的动态反馈。该知识点位于网络协议栈与分布式系统设计的交汇处，是反向代理、API 网关、服务发现与流量治理的核心组件。专业工程师必须掌握其原理，因为负载均衡策略直接决定了系统的容量极限、故障恢复能力与成本效率，且在实际调优中需要根据业务特征选择或组合策略，错误选择可能导致资源倾斜、请求堆积或单点过载。

2. 底层原理剖析

轮询的核心机制是一个游标（index）在节点列表中循环前进，每次请求命中当前节点后游标加一并取模，数学上等价于对请求序号 n 做 (n % N) 映射到节点 i。该算法不关注任何节点状态，仅保证在理想情况下请求均匀分布，但若各节点处理能力不同，则慢节点会成为瓶颈。

加权轮询在轮询基础上为每个节点赋予权重 w_i，目标是使节点在单位时间内接收的请求比例约等于 w_i / Σw。实现上常用平滑加权轮询（Nginx 实现），维护每个节点的当前有效权重 current，每轮选择 current + weight 最大者，选后将当前有效权重减去总权重。该算法避免了传统权重轮询在连续分发时可能出现的短时间请求突刺，使高权重节点被分散穿插。

最小连接数则动态维护每个节点当前活跃连接数 conn_i（或并发请求数），每次选择 conn_i 最小的节点。本质是一个贪心策略，以实时并发度作为代理指标模拟节点负载，能自然适应节点处理速度差异与请求耗时差异：处理快的节点连接数下降快，会被更频繁地选中。但需要注意，连接数并不等于 CPU/内存占用，长连接与短连接场景下其有效性不同。

与前端已有知识的对比：JS 中数组的 reduce 或 redux 中间件链中的调度顺序，本质是编译期/运行期的固定控制流；而负载均衡算法则是动态多目标选择，属于资源调度范畴。另一个可类比的是浏览器的 Fetch 并发控制或 HTTP/2 多路复用中的流调度，但底层权衡维度不同。前端的任务队列调度（如 React 的可中断渲染）是单线程内的优先级抢占，而负载均衡是多节点间的分布式决策，前者依赖事件循环，后者依赖网络状态广播与一致性。

4. 常见误区与进阶思考

认知误区一：轮询就是最公平的算法。事实上轮询只保证请求数量均等，不考虑请求成本。若后端节点性能异构，或请求处理时间差异大，轮询会让慢节点积压请求，造成整体延迟上升。生产环境中纯轮询仅适用于同规格、同无状态服务且请求成本相近的场景。

认知误区二：最小连接数永远优于轮询。最小连接数依赖连接数作为负载信号，但当请求全部为短连接（如 HTTP 短连接）时，连接数剧烈波动，算法容易抖动；若后端为 HTTP/2 多路复用，一个连接上可承载大量并发流，此时最小连接数反而会错误均衡。另外，若各节点已处于过载状态，最小连接数不会主动避免把请求发给已经过载但连接数偏低的节点。

思考题：假设后端两个节点，处理能力分别为每秒 100 和 200 个请求，请求到达率恒定 150 每秒，每个请求固定耗时 10ms。分别使用加权轮询（权重比 1:2）和最小连接数，长期运行后两个节点的连接数平均值各是多少？请从稳态概率角度推导，并说明哪种算法更接近最优。
