每日基础技术总结 · 2026-09-04 · 命令注入与 SSRF 服务端请求伪造

📚 今日主题

命令注入与 SSRF 服务端请求伪造（安全进阶（Web / 认证授权 / 密码学））

1. 核心概念速览

命令注入（Command Injection）与 SSRF（Server-Side Request Forgery，服务端请求伪造）均属于基于‘信任边界混淆’的注入类攻击。命令注入的本质是将用户可控数据作为系统 shell 或原生进程执行的指令参数拼接，利用 Shell 的分号、管道符等元字符劫持执行流；SSRF 的本质是后端服务器在未经严格校验的情况下，利用自身权限发起 HTTP/HTTPS/DNS/TCP 请求，从而突破网络隔离策略，访问内网资源或利用云环境元数据服务。二者均为后端逻辑处理层对输入源信任过度的直接后果，是 Web 应用从单纯的数据渲染向资源交互扩展后产生的典型安全风险。掌握其机制对于构建零信任架构、理解云原生安全边界及防御自动化扫描至关重要。

2. 底层原理剖析

  1. 命令注入底层机制：操作系统通过 execve 或类似系统调用加载进程。当后端代码使用字符串拼接构造命令行参数时，若未进行沙箱化或白名单限制，攻击者可通过注入 ; && || $() ` 等 Shell 特殊字符，改变原本意图执行的子进程上下文。这类似于前端 JS 中 eval() 执行非受控字符串，但层级更高，直接操作 OS 进程表。

  2. SSRF 底层机制：后端服务端程序作为客户端发起出站连接（Outbound Connection）。关键在于‘身份切换’：请求发起者不再是浏览器端的访客，而是拥有内网访问权限的后端服务实例（如 Docker 容器、K8s Pod 或云服务器 ECS/EC2）。SSRF 利用了 DNS 解析、URL 重定向以及常见协议（HTTP, Gopher, FTP, file://）的差异。例如，Gopher 协议允许构造任意 TCP 数据包，可模拟 Redis/Memcached 命令。

  3. 与前端的对比：前端 XSS 关注 DOM 解析与脚本执行上下文，依赖浏览器的同源策略和 CSP 来缓解；而命令注入和 SSRF 发生在服务器端，涉及操作系统进程隔离、防火墙规则、IAM 权限模型以及内部网络路由。前端通过 JSON.stringify 转义数据防止对象注入，后端必须通过结构化参数传递（如避免 shell 解释器）和白名单 IP 段来防御。

4. 常见误区与进阶思考

  1. 误区：认为仅过滤 ‘http://‘ 或特定关键字即可防御 SSRF。实际上，攻击者可利用 IP 十进制/十六进制转换、DNS Rebinding（DNS 重绑定）、IPv6 括号格式、302 Redirect 链、甚至不同协议的 URL Scheme（如 gopher://, ldap://）绕过简单的字符串匹配。本质防御应基于内网 IP 段的严格白名单校验及禁用不必要的高危协议。

  2. 误区：认为使用后端 SDK 调用云厂商 API 就能完全避免 SSRF。在云原生环境中，若后端代码仍需动态生成外部回调地址或代理外部 URL 请求，而未对目标主机进行前置解析与安全组限制，依然可能通过内网穿透或服务发现机制暴露敏感元数据（如 AWS EC2 Metadata v1/v2）。

思考题：在现代微服务架构中，如何通过 Service Mesh（如 Istio/Linkerd）的 Sidecar 代理机制，在基础设施层而非应用代码层实现更精细的内网出口流量控制以缓解 SSRF？请结合 eBPF 或 iptables 规则阐述其原理。
