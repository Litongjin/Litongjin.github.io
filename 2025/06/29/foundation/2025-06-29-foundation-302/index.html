短链系统设计：发号与 302 重定向（分布式与架构设计）

1. 核心概念速览

短链系统本质是长 URI 到短标识符的双射映射与 HTTP 协议层面的流量转发机制。发号模块负责生成全局唯一、无冲突且具备一定随机性或规律性的短标识（Key），通常涉及分布式 ID 生成算法（如雪花算法变种或 Base62 编码映射）；302 重定向则是利用 HTTP 1.1 状态码 302 Found，通过响应头 Location 字段指示客户端浏览器自动向目标长 URL 发起新请求，实现透明跳转。该知识点处于分布式存储索引层与网络应用协议层的交界，是理解高并发写场景下数据一致性、低延迟读场景下 I/O 优化以及状态无连接特性的基础。专业工程师必须掌握它以处理海量路由数据的写入瓶颈、读取缓存击穿及协议语义的正确性。

2. 底层原理剖析

运行机制分为两个独立阶段：

  1. 发号阶段（写操作）：接收长 URL -> 去重检查（哈希碰撞检测）-> 调用分布式 ID 生成器生成唯一 ShortId -> 将 (ShortId, LongUrl) 存入持久化存储（如 Redis/MySQL）-> 返回 ShortId 供用户分享。
    • 核心约束：ID 生成需保证单调性（可选）、唯一性、紧凑性（便于 Base62 编码压缩长度）。
  2. 重定向阶段（读操作）：客户端请求短链域名的 /{ShortId} -> 后端服务从存储层查询对应 LongUrl -> 校验有效性 -> 构建 HTTP 响应包，设置 Status Code = 302，Header 中插入 Location: -> 清空 Body 直接发送。
    对比前端概念：前端路由（如 React Router）是客户端 JS 对 DOM History API 的操作，属于应用层逻辑；而 302 重定向是 Web 服务器遵循 RFC 7231 标准的协议行为，由服务端强制主导，客户端仅执行标准动作。此外，短链 ID 生成类似于前端的 UUID 生成，但短链更强调‘空间局部性’（若采用分段映射）和‘数据库友好性’（避免热点 shard），而非单纯的无序唯一。

[‘误区一：混淆 301 永久重定向与 302 临时重定向的语义及其对 SEO 和缓存的影响。短链通常具有时效性或业务关联性变化，若误用 301，搜索引擎会将权重完全转移至旧链，且中间代理服务器会强缓存 301 响应，导致无法及时更新目标地址或下线短链。\n误区二：忽视 Base62 编码在短链 ID 生成中的熵值问题。简单自增 ID 进行 Base62 转换可能导致短链被遍历猜测（ID 爆破），从而引发恶意刷量或信息泄露。需在发号机制中加入随机干扰位或使用加密序号（SN）而非纯计数。’]
